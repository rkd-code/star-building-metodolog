# KNOWLEDGE_BASE.md: Структура и регламент ведения базы знаний

Данный документ определяет архитектуру базы знаний, входящей в контекст Claude Project (`Project Knowledge`), правила хранения файлов, состав пилотных регламентов, информационную модель данных и структуру связей между нормативными документами компании Star Building.

---

| ID документа | Название регламента | Назначение в базе знаний | Обязательные разделы для ссылок |

## 4. Информационная модель данных и сущности (`03-data-model`)

Система опирается на формализованную модель данных (`03-data-model/entities.md`, интерактивный вид в `03-data-model/data_model.html`, граф связей в `03-data-model/mindmap.html`):
- **Регламент (`РЕГ-ХХХ`)**: 5 обязательных разделов, оцифрованные показатели, матрица ответственности.
- **Карточка регламента (`КАРТ-РЕГ-ХХХ`)**: компактная выжимка входов/выходов и связей.
- **Должность / Роль (`ДОЛЖ-ХХХ`)**: нормативные штатные позиции из `REG-003`.
- **Входной черновик (`ЧЕРН-ХХХ`)**: исходный неструктурированный текст автора.
- **Решение агента (`РЕШ-ХХХ`)**: статус генерации, ссылки на ядро, метки уточнений.
- **Журнал действий (`ЛОГ-ХХХ`)**: пошаговый аудит трансформации черновика.

## 5. Архитектура серверного окружения (`04-environment`)

Серверная среда агента на платформе Гермес организована по 5 изолированным зонам:
- **Зона проекта (`/home/roman/`)**: репозиторий, документация, спецификации, схемы и отчеты.
- **Зона настроек (`~/.hermes/config.yaml`)**: параметры автономного режима и долгосрочной памяти.
- **Зона данных (`knowledge_base/`, `~/.hermes/state.db`)**: реестры, карточки, утвержденные регламенты.
- **Зона журналов (`~/.hermes/logs/`)**: аудит решений, ротация логов (до 50 МБ).
- **Зона секретов (`~/.hermes/.env`)**: закрытые ключи API с жесткими правами доступа (`600`).

## 6. Внешние интеграции и потоки данных (`05-integrations`)

- **Первая версия (v1.0 MVP):** веб-интерфейс проекта Claude Project + локальное файловое хранилище (без внешних API).
- **Следующие версии (v2.0+):** Telegram-бот для прорабов, публикация в базу знаний Битрикс24, маршруты согласования в 1С:ДО / СЭД.
- **Принцип безопасности:** обязательное подтверждение человеком (методологом/руководством) перед публикацией регламентов.

## 7. Сервер инструментов и протокол контекста модели (`06-tools`)

Архитектура инструментов агента разделена на 4 группы:
- **Чтение:** `читать_базовый_регламент`, `получить_карточки_процессов`, `получить_реестр_должностей`.
- **Анализ:** `проверить_роли_черновика`, `проверить_конфликты_с_ядром`, `проверить_полноту_по_стандарту`.
- **Подготовка изменений:** `сформировать_проект_регламента`, `сгенерировать_карточку_процесса`.
- **Выполнение действий:** `сохранить_черновик_регламента`, `опубликовать_утвержденный_регламент` (требует визы человека).

## 9. Уточнения бизнес-логики и правила версионности (`08-refinement`)

Зафиксированы 4 правила доведения логики до совершенства:
1. **Интерактивные уточнения (1-А):** автор черновика сам отвечает на вопросы агента по недостающим срокам и формам.
2. **Межрегламентные конфликты (2-Б):** при противоречии операционных регламентов формируется задача на актуализацию затронутого `РЕГ-ХХХ`.
3. **Голосовой ввод (3-Б):** прием аудиосообщений от прорабов с авто-транскрибацией в текст.
4. **Двухуровневые версии (4-Б):** `0.1` (черновик) ➔ `1.0` (база) ➔ `1.x` (правка сроков/ролей) ➔ `2.0` (полный рефакторинг).

## 10. Дорожная карта и этапы разработки (`09-roadmap`)

Поэтапный план развития системы от пилота до корпоративного уровня (`09-roadmap/roadmap.html`):
- **Этап 1 (v1.0 MVP, 2–3 дня):** Claude Project, 5–10 документов Ядра, текстовые черновики.
- **Этап 2 (v1.1, 1–2 недели):** голосовой ввод от прорабов, интерактивный опрос автора, 15–20 регламентов.
- **Этап 3 (v1.5, 3–4 недели):** все 45 регламентов, сервер инструментов, авто-реестр, плановый аудит.
- **Этап 4 (v2.0 Enterprise):** Telegram-бот, Битрикс24, маршруты согласования в 1С:ДО / СЭД.

## 11. Универсальный корпоративный агент и автогенерация документов (`10-general-assistant`)

Расширение ТЗ до единого агента общего использования:
- **Контур кодификатора:** сборка регламентов по 5 разделам для методологов и руководителей.
- **Контур консультанта:** решение любого вопроса сотрудника со ссылками на пункты `РЕГ-001`..`005`.
- **Автогенерация шаблонов:** выдача готовой предзаполненной служебной записки, коммерческого акта, заявки или претензии вместе с решением проблемы.

Интерактивная карта связей `12-mindmap-update/mindmap.html` объединяет оба контура системы:

## 14. Контроль качества базы знаний и приемочные тесты (`02-tests`)

База знаний верифицируется через комплекс приемочных испытаний:
- **`TC-01 (Happy Path)`**: Валидация преобразования черновика в 5 разделов (`02-tests/test_01_happy_path.md`).
- **`TC-02 (Edge Cases)`**: Проверка реакции на неполноту данных (`[ТРЕБУЕТ УТОЧНЕНИЯ]`), сленг и попытки нарушения ядра (`02-tests/test_02_edge_cases.md`).
- **`TC-03 (Safe Stop)`**: Механизм безусловного отклонения черновиков, нарушающих Кодекс `REG-001` (`02-tests/test_03_safe_stop.md`).
- **`TC-04 (Детерминизм и объяснимость)`**: 100% повторяемость структуры и обоснованность ссылочной базы (`02-tests/test_04_idempotency_and_explainability.md`).
- **`TC-05 (Допущения тестов)`**: Реестр спорных ожиданий и метрик допустимых вариаций (`02-tests/test_assumptions.md`).

## 15. Формат карточки регламента (`01_КАРТОЧКИ`)

Каждая карточка формируется промптом «Карточник» по следующему шаблону:

```markdown
# КАРТОЧКА: [ID] [Название]

- **ID:** REG-XXX
- **Владелец процесса:** [Должность по REG-003]
- **Цель процесса:** [1 предложение]
- **Вход процесса:** [Триггер, документы, материалы]
- **Выход процесса:** [Результат, артефакты]
- **Ключевые роли:** [Список ролей по REG-003 с функциями]
- **Связанные документы:** [Прямые ссылки на REG-YYY]
- **Точки контроля и сроки:** [Контрольные точки и SLA]
```

## 16. Протокол обновления базы знаний

1. **Добавление нового регламента:**
   - После утверждения финальной версии руководством документ помещается в `02_ПОЛНЫЕ-ТЕКСТЫ`.
   - Через промпт «Карточник» генерируется файл в `01_КАРТОЧКИ`.
   - В `00_РЕЕСТР/reestr-reglamentov.md` добавляется строка с ID и матрицей владения.
   - Обновленные файлы синхронизируются с `Project Knowledge` в Claude Project.
2. **Периодический аудит (v2.0):**
   - Раз в 6 месяцев все карточки прогоняются через промпт «Сверщик» для выявления устаревших или противоречащих друг другу пунктов.
