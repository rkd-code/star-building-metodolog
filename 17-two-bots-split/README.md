# 17-two-bots-split: Разделение на 2 независимых бота

В каталоге зафиксирована архитектура физического разделения системы на двух специализированных ботов с независимыми токенами и назначением.

---

## 🤖 Бот 1: «Кодификатор регламентов» (`@ReglamentSB_bot`)
- **Аудитория:** Сотрудники, руководители, методологи.
- **Назначение:** ТОЛЬКО разработка новых документов:
  1. Прием черновиков (текст, голос, файлы `.docx`, `.pdf`, изображения).
  2. Заявки на создание регламентов, инструкций и техкарт с нуля.
  3. Упаковка строго по 5 разделам и сохранение в папку `01_В_РАБОТЕ`.
  4. Автоматическая выдача автономного UTF-8 HTML-файла в Telegram (`send_document`).
  5. Экспорт в Google Docs (`application/vnd.google-apps.document`) при настроенном защищённом OAuth.
  6. Детерминированная повторная выдача артефактов («выдай файл / HTML / Google Docs») без повторного обращения к LLM на основе кэша последнего регламента пользователя.
- **Учетные данные:** хранятся только вне Git; значение в документации не указывается.

---

## 🤖 Бот 2: «Корпоративный консультант» (Второй бот)
- **Аудитория:** ВСЕ сотрудники компании.
- **Назначение:** ТОЛЬКО решение рабочих вопросов по действующим стандартам:
  1. Ответы на вопросы со ссылками на пункты `РЕГ-001`..`010`.
  2. Пошаговые алгоритмы («Что делать сейчас / Что запрещено»).
  3. Автогенерация предзаполненных служебных записок, актов брака и заявлений.

---

## Экспорт регламентов в HTML и Google Docs (FN-013)

Архитектура модуля экспорта (`artifact_exporter.py`):
1. **Детерминированное распознавание намерений:** перехват команд выгрузки (`файл`, `html`, `google docs`, `скачать`, `выдай файл`) до обращения к LLM.
2. **Строгая валидация структуры (`is_complete_regulation`):** проверка ровно 5 обязательных разделов в строгом порядке с непустым содержимым каждого раздела.
3. **Долговечное хранилище артефактов (`PersistentArtifactStore`):** SQLite с сохранением при перезапуске процесса, изоляцией `user_id` и fail-closed при повреждениях.
3. **Безопасная генерация HTML (`HtmlRenderer`):** автономный HTML с UTF-8, полной экранизацией XSS/HTML-тегов и адаптивными корпоративными стилями Star Building.
4. **Санитизация имен файлов (`FilenameSanitizer`):** защита от path traversal и ограничение длины имени файла.
5. **Адаптер Google Drive (`GoogleDriveAdapter`):**
   - Проверка безопасности OAuth токена (`OAuthTokenValidator`): канонический каталог, `lstat`, запрет symlink/hardlink, проверка UID, права `<= 0600`, безопасный atomic refresh.
   - Идемпотентность экспорта: переиспользование `gdocs_url` и per-user блокировки гарантируют ровно один вызов Google Drive API при конкурентных запросах.
   - При отсутствии токена или ошибках API работает в режиме graceful failure: не блокирует выдачу HTML и возвращает стабильное безопасное сообщение без утечки путей и секретов.
   - Валидация URL Google Docs строго по шаблону `https://docs.google.com/document/d/<id>/edit`.

## Надежный запуск и контроль

Оба бота работают как независимые пользовательские службы `systemd`:

- `star-building-codifier.service` — «Смотритель»;
- `star-building-consultant.service` — «Ом».

Службы автоматически запускаются после перезагрузки и перезапускаются при отказе. Учетные данные хранятся вне Git в `/home/roman/.config/star-building/bots.env` с правами `0600`.

Проверка состояния без вывода учетных данных:

```bash
python3 /home/roman/17-two-bots-split/bot_healthcheck.py
systemctl --user status star-building-codifier.service
systemctl --user status star-building-consultant.service
```

Фоновая задача Hermes выполняет эту проверку каждые 5 минут и сообщает пользователю только при отказе. Версионные образцы служб находятся в `systemd/`.

## Правило безопасности

После обнаружения учетных данных в старой истории Git токены обоих ботов необходимо перевыпустить через BotFather. Старые токены не считаются безопасными, даже если репозиторий позднее стал приватным.
