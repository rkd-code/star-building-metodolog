# Спецификация инструментов и команд сервера контекста модели

Команды разделены на 4 функциональные группы. Для каждой команды определены параметры, права и требования безопасности.

---

## ГРУППА 1. Инструменты чтения данных

### 1. `читать_базовый_регламент`
- **Назначение:** Получение полного текста или отдельных разделов ядровых регламентов (`РЕГ-001` Кодекс, `РЕГ-002` Коммуникации, `РЕГ-003` Оргструктура).
- **Входные данные:** `код_регламента` (строка, например: `РЕГ-002`), `раздел` (строка, необязательно).
- **Ожидаемый результат:** Структурированный текст запрашиваемого регламента.
- **Источник данных:** Локальное хранилище `knowledge_base/02_ПОЛНЫЕ-ТЕКСТЫ/`.
- **Права доступа:** Только чтение (права пользователя `roman`).
- **Возможные ошибки:** Документ не найден, запрошен несуществующий раздел.
- **Подтверждение человеком:** **Не требуется** (безопасная операция чтения).

### 2. `получить_карточки_процессов`
- **Назначение:** Быстрое чтение кратких карточек всех регламентов для поиска связей и владельцев процессов.
- **Входные данные:** `фильтр_по_роли` (строка, необязательно), `список_кодов` (массив строк, необязательно).
- **Ожидаемый результат:** Список структурированных карточек процессов (входы, выходы, роли, сроки).
- **Источник данных:** Локальное хранилище `knowledge_base/01_КАРТОЧКИ/`.
- **Права доступа:** Только чтение.
- **Возможные ошибки:** Пустой каталог карточек, повреждение формата разметки.
- **Подтверждение человеком:** **Не требуется**.

### 3. `получить_реестр_должностей`
- **Назначение:** Чтение утвержденного справочника должностей из оргструктуры (`РЕГ-003`) для нормализации ролей.
- **Входные данные:** `подразделение` (строка, необязательно).
- **Ожидаемый результат:** Перечень официальных наименований штатных единиц и их синонимов.
- **Источник данных:** Регламент `РЕГ-003` и справочник `ДОЛЖ-ХХХ`.
- **Права доступа:** Только чтение.
- **Возможные ошибки:** Подразделение не найдено.
- **Подтверждение человеком:** **Не требуется**.

---

## ГРУППА 2. Инструменты анализа и проверки

### 4. `проверить_роли_черновика`
- **Назначение:** Сопоставление упоминаемых в черновике должностей со справочником `РЕГ-003`.
- **Входные данные:** `список_упоминаний_ролей` (массив строк: «прораб», «закупщик», «технарь»).
- **Ожидаемый результат:** Таблица сопоставления: исходный термин ➔ официальная должность из `РЕГ-003` либо отметка «Не найдено в оргструктуре».
- **Источник данных:** Справочник `РЕГ-003`.
- **Права доступа:** Анализ в оперативной памяти (без модификации файлов).
- **Возможные ошибки:** Омонимичные или двусмысленные названия.
- **Подтверждение человеком:** **Не требуется**.

### 5. `проверить_конфликты_с_ядром`
- **Назначение:** Автоматический поиск противоречий черновика с Кодексом (`РЕГ-001`) и Регламентом коммуникаций (`РЕГ-002`).
- **Входные данные:** `текст_проекта_регламента` (строка).
- **Ожидаемый результат:** Отчет о противоречиях: статус (Согласовано / Обнаружен конфликт / Безопасная остановка), список нарушенных пунктов ядра.
- **Источник данных:** Ядро `РЕГ-001`, `РЕГ-002`.
- **Права доступа:** Анализ в оперативной памяти.
- **Возможные ошибки:** Ошибки логического сопоставления.
- **Подтверждение человеком:** **Не требуется**.

### 6. `проверить_полноту_по_стандарту`
- **Назначение:** Проверка соблюдения стандарта 5 обязательных разделов, наличия измеримых показателей и матрицы ответственности.
- **Входные данные:** `текст_проекта_регламента` (строка).
- **Ожидаемый результат:** Список замечаний: пропущенные разделы, неизмеримые формулировки, список сгенерированных меток `[ТРЕБУЕТ УТОЧНЕНИЯ]`.
- **Источник данных:** Правила валидации схемы регламента.
- **Права доступа:** Анализ в оперативной памяти.
- **Возможные ошибки:** Некорректный синтаксис разметки.
- **Подтверждение человеком:** **Не требуется**.

## ГРУППА 3. Инструменты подготовки изменений

### 7. `сформировать_проект_регламента`
- **Назначение:** Сборка стандартизированного проекта регламента по 5 обязательным разделам на основе сырого черновика.
- **Входные данные:** `исходный_черновик` (строка), `автор` (строка), `нормализованные_роли` (объект).
- **Ожидаемый результат:** Текст регламента в стандарте v1.0 со статусом `Черновик для согласования (v0.1)`.
- **Источник данных:** Генеративный модуль агента.
- **Права доступа:** Формирование структуры в оперативной памяти.
- **Возможные ошибки:** Неполнота входных данных (выставляются теги уточнений).
- **Подтверждение человеком:** **Не требуется** (результат передается на вычитку).

### 8. `сгенерировать_карточку_процесса`
- **Назначение:** Формирование сжатой карточки регламента по шаблону промпта «Карточник».
- **Входные данные:** `текст_утвержденного_регламента` (строка), `код_регламента` (строка).
- **Ожидаемый результат:** Текст карточки (`КАРТ-РЕГ-ХХХ`).
- **Источник данных:** Текст регламента.
- **Права доступа:** Формирование текста в памяти.
- **Возможные ошибки:** Не удалось выделить границы процесса (вход/выход).
- **Подтверждение человеком:** **Не требуется**.

---

## ГРУППА 4. Инструменты выполнения действий

### 9. `сохранить_черновик_регламента`
- **Назначение:** Запись сформированного черновика регламента в рабочую директорию проекта.
- **Входные данные:** `код_регламента` (строка: `РЕГ-004-ЧЕРНОВИК`), `содержимое_файла` (строка).
- **Ожидаемый результат:** Подтверждение создания файла и путь к нему.
- **Источник данных:** Локальная файловая система `knowledge_base/`.
- **Права доступа:** Запись в каталог проекта.
- **Возможные ошибки:** Ошибка прав доступа к диску, нехватка дискового пространства.
- **Подтверждение человеком:** **Не требуется** (сохранение рабочего черновика).

### 10. `опубликовать_утвержденный_регламент`
- **Назначение:** Перевод регламента в статус `Утвержден`, сохранение в `02_ПОЛНЫЕ-ТЕКСТЫ`, генерация карточки и обновление сводного реестра `00_РЕЕСТР/reestr-reglamentov.md`.
- **Входные данные:** `код_регламента` (строка: `РЕГ-004`), `реквизиты_утверждения` (дата, номер приказа, ФИО руководителя).
- **Ожидаемый результат:** Зафиксированный в ядре регламент, созданная карточка и обновленная строка в реестре.
- **Источник данных:** Хранилище базы знаний.
- **Права доступа:** Запись в защищенные каталоги базы знаний.
- **Возможные ошибки:** Нарушение ссылочной целостности, конфликт идентификаторов в реестре.
- **Подтверждение человеком:** **ОБЯЗАТЕЛЬНО.** Действие выполняется только после явного подтверждения методологом или руководством.
