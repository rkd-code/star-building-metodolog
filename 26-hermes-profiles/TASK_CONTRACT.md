# Договор передачи кодовой задачи

Общий оркестратор передает разработчику кодовую работу только в этой структуре.

```markdown
# Задача: <краткое название>

## 1. Проект
- Код проекта: <код Hermes Project>
- Локальный путь: <абсолютный путь>
- Удаленный репозиторий: <адрес>
- Исходная ветка: <ветка>
- Рабочая среда: <Kanban worktree / обычная ветка>

## 2. Цель
- Требуемый результат:
- Деловая причина:
- Текущее неправильное поведение:
- Ожидаемое поведение:

## 3. Границы
- Разрешено менять:
- Нельзя менять:
- Совместимость:
- Данные и безопасность:

## 4. Контекст Graphify
- Путь к графу:
- Выполненный запрос:
- Ключевые узлы:
- Предполагаемые файлы:
- Зависимые компоненты:
- Риски влияния:

## 5. Критерии приемки
1. <измеримый критерий>
2. <измеримый критерий>
3. <измеримый критерий>

## 6. Обязательные проверки
- Синтаксис/статический анализ:
- Узкие испытания:
- Полные испытания:
- Сборка/запуск:
- Проверка безопасности:
- Проверка Graphify после изменения:

## 7. Git
- Шаблон имени ветки:
- Требование к сообщению фиксации:
- Push рабочей ветки: обязателен
- Слияние в основную ветку: запрещено без отдельного решения
- Принудительная отправка: запрещена

## 8. Обновление сведений
- KNOWLEDGE_BASE.md:
- DECISIONS.md:
- PROJECT_MAP.md:
- Схемы/реестры:
- graphify-out:

## 9. Формат отчета
- Перечень файлов и изменений
- Команды и фактический результат проверок
- Рабочая ветка
- Идентификатор фиксации
- Подтверждение push
- Обновление Graphify
- Ограничения и риски
```

## Правила договора

1. Поля нельзя заменять общими словами «исправить», «улучшить» или «проверить» без критерия результата.
2. Если данных нет и их нельзя определить инструментами, используется `[ТРЕБУЕТ УТОЧНЕНИЯ: конкретный вопрос]`.
3. Разработчик вправе сузить изменение, если это сохраняет критерии приемки и снижает риск.
4. Расширение области задачи требует комментария в Kanban и решения оркестратора.
5. Отчет разработчика не закрывает задачу автоматически: оркестратор проводит независимую приемку.
