# 26-hermes-profiles: Два независимых профиля Hermes

Подготовлены инструкции для двух изолированных профилей:

- `orchestrator` — принимает любые задачи, выбирает проект, планирует, использует Graphify, передает код разработчику, проводит независимую приемку и отчитывается пользователю.
- `developer` — находит проект, исследует его через Graphify, синхронизирует Git, работает в отдельной ветке/рабочем дереве, меняет и проверяет код, выполняет commit и push, обновляет граф и сведения о проекте.

Профили имеют отдельные настройки, память, сеансы и навыки в:

```text
~/.hermes/profiles/orchestrator/
~/.hermes/profiles/developer/
```

## Файлы

- `orchestrator/SOUL.md` — постоянная роль и рабочий цикл оркестратора.
- `developer/SOUL.md` — постоянная роль и рабочий цикл разработчика.
- `TASK_CONTRACT.md` — обязательная структура передачи кодовой задачи.
- `PROJECT_CONTEXT_TEMPLATE.md` — шаблон `.hermes.md` для каждого репозитория.
- `setup_profiles.sh` — подготовленный сценарий первоначального создания профилей.
- `register_project.sh` — регистрация одного проекта в обоих профилях.

## 1. Почему используются профили

Hermes хранит профили изолированно. Каждый профиль получает собственные:

- `config.yaml`;
- `.env` и учетные данные;
- `SOUL.md`;
- навыки;
- память и сеансы;
- список Hermes Projects.

Доска Kanban используется как проверяемый договор между профилями. Для кодовой задачи применяется изолированное рабочее дерево Git.

## 2. Первоначальная установка

Graphify уже установлен в среде `/srv/hermes-agent/venv`, но его навык необходимо добавить в Hermes до клонирования профилей:

```bash
/srv/hermes-agent/venv/bin/graphify install --platform hermes
```

После этого можно выполнить:

```bash
bash /home/roman/26-hermes-profiles/setup_profiles.sh
```

Сценарий:

1. проверяет наличие Hermes и Graphify;
2. не перезаписывает существующие одноименные профили;
3. создает `orchestrator` и `developer` из текущего профиля `default`;
4. устанавливает подготовленные `SOUL.md`;
5. задает описания профилей для маршрутизации Kanban;
6. проверяет наличие навыка Graphify в обоих профилях.
7. включает автоматическое сжатие контекста до 50% и устанавливает предел 100 итераций для основной работы и делегированных задач.

> Клонирование переносит текущую конфигурацию и учетные данные в отдельные файлы профилей. Дальнейшие изменения одного профиля не изменяют другой.

## 3. Регистрация проектов

Каждый проект необходимо зарегистрировать в обоих профилях, поскольку реестр Hermes Projects является профильным.

Пример для Star Building:

```bash
bash /home/roman/26-hermes-profiles/register_project.sh \
  star-building \
  "Star Building" \
  /home/roman \
  main
```

Сценарий:

- проверяет, что путь является Git-репозиторием;
- определяет удаленный репозиторий;
- создает или подтверждает Kanban-доску с кодом проекта;
- регистрирует одинаковый проект в обоих профилях;
- привязывает проект к доске;
- фиксирует исходную ветку в описании проекта каждого профиля.

Для каждого репозитория рекомендуется создать `.hermes.md` по `PROJECT_CONTEXT_TEMPLATE.md`.

## 4. Создание и обновление Graphify

В корне каждого проекта:

```bash
cd <путь-к-проекту>
/srv/hermes-agent/venv/bin/graphify . --no-viz
```

Перед анализом существующего проекта:

```bash
/srv/hermes-agent/venv/bin/graphify query \
  "Какие модули и зависимости затрагивает задача?" \
  --graph graphify-out/graph.json
```

После изменения кода:

```bash
/srv/hermes-agent/venv/bin/graphify update .
/srv/hermes-agent/venv/bin/graphify affected "<измененный узел>" \
  --graph graphify-out/graph.json
```

Если `graphify` доступен в `PATH`, абсолютный путь можно заменить командой `graphify`.

## 5. Передача задачи разработчику

Оркестратор создает карточку:

```bash
hermes kanban create "Исправить <краткое название>" \
  --assignee developer \
  --project <код-проекта> \
  --workspace worktree \
  --goal \
  --goal-max-turns 100 \
  --body "$(cat <подготовленная-карточка>.md)"
```

Карточка заполняется по `TASK_CONTRACT.md`.

Для запуска обработчика должна работать служба Hermes:

```bash
hermes gateway status
hermes gateway start
```

Если Kanban временно недоступен:

```bash
hermes -p developer --worktree chat -q "<полный договор задачи>"
```

## 6. Самостоятельность профилей

Оба профиля без дополнительных вопросов выполняют обычные шаги внутри однозначно выбранного проекта:

- чтение, Graphify и анализ Git;
- установка зависимостей в среде проекта;
- планирование и создание рабочих карточек;
- создание отдельной ветки/рабочего дерева;
- изменение кода и испытаний;
- локальный запуск, сборка и проверки;
- исправление выявленных дефектов;
- commit и push рабочей ветки;
- обновление Graphify и проектной документации.

Для обоих профилей действуют единые пределы:

- `compression.enabled = true`;
- `compression.target_ratio = 0.50` — после каждого сжатия сохраняется 50% рабочего объема;
- `agent.max_turns = 100` — не более 100 итераций основной задачи;
- `delegation.max_iterations = 100` — не более 100 итераций делегированной задачи;
- для Kanban-задач с целевым циклом используется `--goal-max-turns 100`.

Отдельное решение пользователя остается обязательным для:

- слияния в основную ветку;
- принудительной отправки;
- развертывания в рабочую среду;
- необратимых изменений данных;
- операций с секретами и правами;
- внешней публикации от имени компании;
- платных операций;
- переноса документов в утвержденный контур.

## 7. Проверка после установки

```bash
hermes profile show orchestrator
hermes profile show developer

test -f ~/.hermes/profiles/orchestrator/SOUL.md
test -f ~/.hermes/profiles/developer/SOUL.md

test -f ~/.hermes/profiles/orchestrator/skills/graphify/SKILL.md
test -f ~/.hermes/profiles/developer/skills/graphify/SKILL.md

hermes kanban assignees
```

Пробный запрос без изменения проекта:

```bash
hermes -p orchestrator chat -q \
  "Покажи зарегистрированные проекты, выбери Star Building и объясни, как передашь кодовую задачу разработчику. Ничего не изменяй."
```

Пробный запрос разработчику:

```bash
hermes -p developer chat -q \
  "Найди проект Star Building через Hermes Projects и Graphify. Покажи корень Git, удаленный репозиторий и ключевые узлы. Ничего не изменяй."
```

## 9. Важные ограничения

- В профилях не хранятся секреты в `SOUL.md`, инструкциях или Git.
- Проектные правила размещаются в `.hermes.md` или `AGENTS.md` самого репозитория.
- `.hermes.md` предпочтителен для наследования правил по подпапкам; `AGENTS.md` Hermes загружает только из текущей рабочей папки.
- Файлы роли короче ограничения контекста Hermes в 20 000 символов.
- Фоновые подагенты не заменяют долговечную передачу через Kanban.
- Оркестратор не закрывает кодовую задачу только по отчету разработчика — обязательна независимая проверка.
