# 29-employee-testing-service: «Экзаменатор Star Building»

## Решение

Предлагается создать отдельный корпоративный сервис **«Экзаменатор Star Building»** для проверки знаний технологий, должностных инструкций и утвержденных регламентов.

Это не опросник и не часть «Ома»: сервис хранит версии банка вопросов, формирует персональные тесты, фиксирует попытки и выдает сотруднику и руководству проверяемый результат.

## Почему отдельный сервис

Простые формы подходят для разового опроса, но плохо решают постоянную аттестацию:

- не обеспечивают надежную версионность более 100 вопросов;
- не связывают вопрос с конкретным пунктом регламента;
- не формируют разные наборы по должностям;
- не дают полноценный журнал попыток и изменений;
- не позволяют безопасно менять вопрос, сохраняя историю старого результата.

«Экзаменатор» должен быть отдельным модулем, связанным с нормативной базой Star Building и оргструктурой.

## Пользовательский путь

1. Сотрудник получает назначение на тест.
2. Открывает тест по защищенной ссылке или через корпоративный вход.
3. Видит правила: число вопросов, время, порог и число доступных попыток.
4. Отвечает на вопросы последовательно.
5. Система автоматически сохраняет каждый ответ.
6. После завершения сотрудник получает:
   - общий балл;
   - статус «пройден» или «не пройден»;
   - результат по темам;
   - перечень тем для повторного изучения;
   - ссылки на пункты утвержденных регламентов.
7. Уполномоченный руководитель видит результаты подразделения, просрочки, повторные попытки и слабые темы.

## Состав первой версии

### 1. Банк вопросов

Поддерживает не менее 500 записей без изменения схемы. Каждый вопрос содержит:

- уникальный код;
- тему;
- должности, которым он назначается;
- тип вопроса;
- формулировку;
- варианты ответа;
- правильный ответ;
- объяснение;
- обязательную ссылку на утвержденный источник;
- сложность;
- статус и версию;
- автора и проверяющего;
- даты создания и проверки.

Вопрос без утвержденного источника нельзя переводить в состояние «Действует».

### 2. Конструктор тестов

Позволяет создать программу проверки по:

- должности из утвержденной оргструктуры;
- подразделению;
- технологии;
- конкретному регламенту;
- вводному обучению;
- повторной аттестации;
- изменению нормативного документа.

### 3. Прохождение

- случайная выборка из разрешенного банка;
- случайный порядок вариантов;
- ограничение времени;
- автоматическое сохранение;
- восстановление после обрыва связи;
- запрет повторной отправки завершенной попытки;
- фиксация версии каждого показанного вопроса.

### 4. Результаты и отчетность

Сотрудник видит только собственные результаты. Уполномоченные лица видят:

- результат по сотруднику;
- результат по должности и подразделению;
- долю прошедших;
- средний балл;
- число попыток;
- темы с наибольшим числом ошибок;
- сотрудников с истекшим сроком проверки;
- динамику по периодам;
- выгрузку в Excel.

### 5. Управление доступом

Предлагаемые контуры доступа:

- **Сотрудник:** проходит назначенные тесты и видит свои результаты.
- **Автор вопросов:** готовит вопросы, но не утверждает их единолично.
- **Проверяющий:** сверяет вопрос с утвержденным источником.
- **Назначающий:** назначает программы сотрудникам в пределах разрешенного контура.
- **Наблюдатель:** видит сводную отчетность без изменения данных.
- **Технический администратор:** управляет системой, но не меняет нормативный смысл вопросов.

Соответствие этих функций официальным должностям требует отдельного утверждения. Новые должности в оргструктуру не вводятся.

## Рекомендуемая архитектура

```text
Сотрудник / руководитель
          │
          ▼
Адаптивный веб-интерфейс
          │
          ▼
Сервис тестирования
    ├── Банк вопросов и версий
    ├── Конструктор программ
    ├── Назначения
    ├── Попытки и ответы
    ├── Оценка
    └── Отчеты
          │
          ▼
Реляционная база данных
          │
          ├── Утвержденная нормативная база
          ├── Оргструктура
          └── Журнал аудита
```

Предлагаемый технический состав первой версии:

- серверная часть: Python и FastAPI;
- база: PostgreSQL;
- интерфейс: React;
- вход: первоначально корпоративная учетная запись или одноразовая ссылка, позднее — Битрикс24;
- уведомления: Telegram и/или Битрикс24;
- развертывание: контейнеры Docker в изолированной среде компании;
- отчетность: экран руководителя и выгрузка Excel.

## Связь с действующей системой

- **Нормативная база P-002:** источник правильных ответов и ссылок.
- **«Ом» P-004:** после результата может объяснить тему, но не изменяет оценку.
- **Битрикс24 P-006:** в будущем передает сотрудников, назначения и уведомления.
- **Hermes P-009:** помогает готовить и проверять вопросы, но не утверждает их автоматически.
- **Graphify P-010:** показывает связи вопроса с регламентом, должностью, технологией и решением.

## Правила достоверности

1. В действующий тест включаются только вопросы со ссылкой на утвержденный документ.
2. Черновые регламенты можно использовать только в учебной песочнице с явной маркировкой.
3. Изменение правильного ответа создает новую версию вопроса.
4. Завершенная попытка всегда хранит снимок версии вопроса.
5. Искусственный интеллект может предложить формулировку, но автор и проверяющий обязаны подтвердить ее.
6. Пароли, токены и ключи не хранятся в банке вопросов и выгрузках.
7. Персональные результаты доступны только в пределах утвержденных прав.

## Этапы внедрения

### Этап 1. Подготовка знаний

1. Назначить владельца сервиса и проверяющих.
2. Утвердить параметры пилота.
3. Выбрать одну должность из действующей оргструктуры.
4. Заполнить не менее 100 вопросов в `question_bank_template.xlsx`.
5. Проверить источник и правильный ответ каждого вопроса.

### Этап 2. Минимальная рабочая версия

1. Реализовать загрузку Excel.
2. Реализовать банк вопросов и версии.
3. Реализовать вход сотрудника и назначение теста.
4. Реализовать прохождение и автоматическую оценку.
5. Реализовать личный результат и простую сводку.
6. Провести испытание на тестовых учетных записях.

### Этап 3. Пилот

1. Загрузить утвержденный банк.
2. Назначить тест пилотной группе.
3. Проверить понятность вопросов и корректность подсчета.
4. Зафиксировать спорные вопросы.
5. Утвердить порядок пересдачи и хранения результатов.

### Этап 4. Корпоративное развертывание

1. Подключить оргструктуру и корпоративный вход.
2. Добавить программы по должностям.
3. Подключить уведомления и просрочки.
4. Добавить управленческие отчеты.
5. Настроить резервное копирование, журнал доступа и мониторинг.

## Критерии готовности пилота

- загружено не менее 100 проверенных вопросов;
- у каждого действующего вопроса есть утвержденный источник;
- завершенная попытка воспроизводимо пересчитывается;
- сотрудник видит собственный результат;
- уполномоченное лицо видит сводку пилотной группы;
- изменение вопроса не меняет старые результаты;
- выгрузка результатов открывается в Excel;
- секреты отсутствуют в исходном коде и выгрузках;
- действия с вопросами и результатами записываются в журнал.

## Итоговая рекомендация

Создавать собственный сервис **«Экзаменатор Star Building»**, а не ограничиваться общей формой. Начать с веб-версии, импорта Excel и одной пилотной должности. Интеграции с Битрикс24, Telegram и расширенная аналитика добавляются после подтверждения корректности банка и правил оценки.
